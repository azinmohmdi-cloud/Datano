# نقشه پیاده‌سازی MVP داشبورد هوشمند Performance Marketing

## تصمیم‌های قطعی محصول و فنی — ۲۰۲۶-۱۰-۱۰

این بخش مرجع تصمیم‌های فعلی است. موارد «تأیید کاربر» مستقیماً از پاسخ کاربر آمده‌اند؛ موارد «انتخاب فنی» با اختیار صریح واگذارشده به Codex انتخاب شده‌اند. این تصمیم‌ها برنامه اجرای آینده‌اند و به معنی وجود قابلیت در کد فعلی نیستند. API، Schema و Migration واقعی باید در وظیفه پیاده‌سازی مربوطه طراحی، تست و مستند شوند؛ این بخش قرارداد endpoint فرضی ایجاد نمی‌کند.

### مرجع، معماری و دامنه

- **تأیید کاربر:** معماری هدف Modular Monolith/Clean Architecture با FastAPI و Next.js اختصاصی، PostgreSQL، SQLAlchemy 2، Alembic و Celery/Redis مصوب است. جایگزینی Looker Studio نیاز به تأیید دوباره ندارد. تغییر بعدی این معماری همچنان نیازمند درخواست کاربر است.
- **تأیید کاربر:** سند [UX](datano-ux-pages-.md) مرجع نهایی صفحات و دامنه پنل مدیر است؛ پنل مدیر فقط مشاهده اطلاعات نمایشی کاربران و وضعیت اتصالات را دارد. ویرایش/مسدودسازی کاربر، تغییر تنظیمات و مدیریت قواعد در پنل خارج از MVP هستند.
- **تأیید کاربر:** پنج موجودیت دامنه `User`، `Website`، `Integration`، `AnalyticsData` و `Recommendation` مبنای مرحله فعلی‌اند. گزارش نمای مشتق‌شده از داده است؛ قواعد تنظیمات نسخه‌دار بک‌اند هستند. جدول‌های فنی نشست، credential یا وضعیت تأیید، در صورت نیاز واقعی، این تصمیم را به الزام «فقط پنج جدول SQL» تبدیل نمی‌کنند. موجودیت دامنه اضافه و ماژول جدید خودکار ساخته نشود.
- **انتخاب فنی:** مرزهای شش حوزه Identity، Websites، Integrations، Analytics، Recommendations و Reporting مفهومی‌اند؛ ساختار موجود `Backend/app/` و لایه‌های فعلی حفظ شوند. نمونه قدیمی `src/modules` دستور مهاجرت پوشه‌ها نیست. Reporting فعلاً خواندن/ترکیب داده است، نه موجودیت یا سرویس مستقل.
- **تأیید کاربر:** امکانات MVP فعلاً برای کاربران رایگان‌اند؛ پرداخت، اشتراک و محدودیت مبتنی بر پلن ساخته نشود. کنترل نرخ فنی برای امنیت و سهمیه API پابرجاست.
- **انتخاب دامنه:** Excel و جت‌سیو خارج از MVP فعلی‌اند؛ توسعه آن‌ها به وظیفه جداگانه نیاز دارد. پیش‌نمایش لندینگ تصویر/نمای توضیحی مشخصاً برچسب‌خورده است؛ دموی عمومی تعاملی یا داده ساختگی به‌جای داده حساب ساخته نشود. CTA آن کاربر را به همان پیش‌نمایش صفحه می‌برد؛ CTA شروع استفاده به ثبت‌نام می‌رود.
- **تأیید کاربر:** همین اسناد Markdown منابع کافی پروژه‌اند. RFP، پروپوزال اصلی و draw.io پیش‌نیاز توسعه نیستند؛ ادعاهای تاریخی درباره آن‌ها قرارداد مستقل محسوب نمی‌شوند.

### هویت، نقش‌ها و نشست

- **تأیید کاربر:** ورود با ایمیل است. فرم ثبت‌نام نام، نام خانوادگی، ایمیل و رمز/تکرار رمز دارد؛ username از قرارداد عمومی هدف حذف می‌شود. username فعلی فقط جزئیات سازگاری پیاده‌سازی قدیمی است و تغییر آن به Migration/هماهنگی API در وظیفه هویت نیاز دارد.
- **انتخاب فنی:** ایمیل برای جست‌وجوی حساب و یکتایی با trim و lowercase یکسان‌سازی می‌شود؛ حذف نقطه یا بخش `+` و قواعد اختصاصی Gmail انجام نشود. مقدار ورودی معتبر برای نمایش قابل حفظ است؛ کلید canonical سمت سرور یکتا باشد.
- **تأیید کاربر:** ثبت‌نام عادی خودکار حساب فعال با نقش `User` ایجاد می‌کند؛ تأیید ایمیل شرط استفاده عادی نیست. نقش اولیه از درخواست یا browser storage پذیرفته نشود.
- **تأیید کاربر + انتخاب امنیتی:** ایمیل‌های مدیر توسط تنظیمات خصوصی بک‌اند تعیین می‌شوند. نقش `Admin` فقط پس از اثبات مالکیت ایمیل allowlist از طریق کد ایمیلی یا provisioning معتبر سمت سرور اعطا می‌شود؛ صرف ثبت‌نام با متن ایمیل مدیر مجوز نمی‌دهد. تا آن زمان حساب فعال `User` است. پنل مدیر صرفاً metadata مجاز را می‌بیند و به داده تحلیلی خصوصی سایت دیگران دسترسی خودکار ندارد.
- **انتخاب فنی:** احراز هویت محصول با نشست opaque سمت سرور است، نه JWT قابل خواندن در مرورگر. PostgreSQL مرجع پایدار نشست‌های قابل لغو است؛ در cookie فقط شناسه تصادفی رمزنگارانه و در storage فقط digest آن نگه‌داری شود. Redis در صورت نیاز cache است و جای کنترل انقضا/لغو را نمی‌گیرد. cookie در production دارای `HttpOnly`، `Secure`، `SameSite=Lax`، `Path=/` و بدون `Domain` باشد؛ از نام با پیشوند `__Host-` استفاده شود. برای توسعه HTTP، استثنای صریح محلی و نام مجزا لازم است.
- cookie مجوز مقابله با CSRF نیست: برای عملیات تغییردهنده کنترل Origin و token ضد CSRF لازم است. استقرار هدف browser و `/api` را روی یک origin HTTPS ارائه می‌کند؛ proxy استقرار نباید قرارداد مسیر FastAPI را تغییر دهد. Google OAuth برای اتصال منابع است، نه ورود به حساب دیتانو.
- **پیش‌فرض فنی قابل تنظیم:** بدون «مرا به خاطر بسپار»، cookie نشست بدون Max-Age، انقضای عدم فعالیت ۳۰ دقیقه و سقف مطلق ۱۲ ساعت دارد. با این گزینه، cookie پایدار، انقضای عدم فعالیت ۷ روز و سقف مطلق ۳۰ روز دارد. سقف مطلق با فعالیت تمدید نشود؛ بستن مرورگر تضمین لغو نشست نیست. شناسه هنگام ورود/تغییر سطح دسترسی عوض شود؛ خروج نشست فعلی و بازیابی رمز همه نشست‌های حساب را باطل کنند. این اعداد پیش‌فرض جدید طراحی‌اند، نه رفتار فعلی JWT.
- **تأیید کاربر:** بازیابی رمز و «مرا به خاطر بسپار» در MVP الزامی‌اند؛ ویرایش اطلاعات شخصی در پروفایل طبق UX مجاز است، ولی انتخاب نقش و فعال‌سازی مدیریتی از پروفایل پذیرفته نشود. تغییر ایمیل ابتدا مالکیت ایمیل جدید را اثبات می‌کند و نقش مدیر پس از تغییر دوباره ارزیابی می‌شود.
- **انتخاب فنی بازیابی:** کد ایمیلی تصادفی ۸رقمی، یک‌بارمصرف و با اعتبار ۱۰ دقیقه؛ حداکثر ۵ تلاش برای هر کد و فاصله ارسال مجدد حداقل ۶۰ ثانیه. digest کد با HMAC و کلید خصوصی سرور ذخیره شود؛ کد جدید قبلی را باطل کند. کنترل نرخ سمت سرور بر حساب و IP، پاسخ یکسان برای ایمیل موجود/ناموجود، و نشست محدود فقط برای تعیین رمز جدید لازم‌اند. بازیابی خودکار وارد حساب نمی‌کند. ارسال از adapter ایمیل سمت سرور با تنظیمات خصوصی SMTP انجام می‌شود؛ بدون سرویس واقعی، قابلیت تحویل‌شده اعلام نشود و کد در لاگ/پاسخ عمومی قرار نگیرد.
- **انتخاب امنیتی رمز جدید:** برای ایجاد/تغییر رمز، ۱۵ تا ۱۲۸ کاراکتر Unicode، بدون اجبار ترکیب حروف و بدون trim یا truncation؛ hash جدید Argon2id با حداقل پارامترهای OWASP و امکان ارتقا. bcrypt قدیمی فقط در مسیر مهاجرت سازگار و تست‌شده پشتیبانی شود؛ رمزهای موجود صرفاً به‌سبب طول جدید بی‌صدا نامعتبر نشوند. dependency یا تغییر hash در این بازبینی مستندات نصب/اجرا نمی‌شود.

دلیل انتخاب نشست سمت سرور، لغو مستقیم و قابل‌آزمون، سادگی چرخه خروج/بازیابی و بی‌نیازی مرورگر از نگه‌داری bearer token برای این محصول وب است. جزئیات دفاعی از [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)، [Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)، [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) و [Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) بررسی شده‌اند؛ زمان‌ها و اعداد بالا انتخاب پروژه‌اند، نه الزامات عددی این منابع.

### سایت و اثبات مالکیت

- **تأیید کاربر:** هر سایت دقیقاً یک مالک دارد؛ عضو مشترک، دعوت و انتقال مالکیت در MVP وجود ندارد. مجوز همه خواندن‌ها/عملیات با شناسه مالک در بک‌اند بررسی شود.
- **انتخاب فنی:** کلید سایت hostname canonical است: lowercase، IDNA و حذف نقطه انتهایی؛ scheme و slash پایانی هویت را عوض نمی‌کنند. URL باید HTTP(S) عمومی، بدون credential و پورت سفارشی باشد؛ path/query/fragment در فرم ثبت سایت پذیرفته نشود. IP، localhost و اهداف شبکه خصوصی رد شوند. همه DNSها و redirectها هنگام هر درخواست تأیید مجدداً در برابر SSRF کنترل شوند.
- `www.example.com` و `example.com` دو hostname مستقل‌اند؛ زیردامنه هم سایت مستقل است. حذف خودکار `www` یا اعطای مجوز زیردامنه به مالک دامنه والد انجام نشود. redirect تأیید فقط در همان hostname و حداکثر سه مرحله مجاز است.
- یک hostname تأییدشده فقط یک ثبت فعال در کل سیستم دارد؛ ثبت دوباره توسط مالک همان سایت را برمی‌گرداند، برای دیگری خطای عمومی «در دسترس نیست» بدون افشای مالک می‌دهد. درخواست تأییدنشده مالکیت ایجاد نمی‌کند؛ رزرو/چالش ۲۴ ساعت اعتبار دارد و پس از آن قابل جایگزینی است. تخصیص یکتا و رقابت درخواست‌ها باید اتمی باشند.
- روش MVP قراردادن `<meta name="datano-verification" content="...">` در HTML صفحه اصلی hostname است؛ challenge تصادفی و مربوط به همان حساب/سایت، با digest ذخیره‌شده و بدون نمایش token در فهرست عمومی. ابتدا HTTPS بررسی شود؛ استفاده از HTTP فقط برای سایتی که صریحاً با HTTP ثبت شده مجاز است. تأیید دامنه به‌تنهایی مجوز property گوگل نیست.
- حذف سایت فقط توسط مالک، اتصالات/کارهای مربوط را لغو و داده‌های وابسته را از دسترس خارج می‌کند؛ ثبت بعدی اثبات تازه می‌خواهد و تاریخچه مالک قبلی منتقل نمی‌شود. بازیابی/انتقال اختلاف مالکیت خارج از MVP است؛ راهکاری خودکار با ادعای مالکیت جدید ساخته نشود.

### اتصال، آمادگی گزارش و KPIها

- **تأیید کاربر:** هر کاربر یک، دو یا هر سه منبع GA4، Search Console و Ads را به انتخاب خود متصل می‌کند. اتصال هر سه شرط داشبورد نیست؛ سرویس انتخاب‌نشده، داده مفقود و خطا صفر محسوب نمی‌شوند.
- هر سایت می‌تواند یک property/account منتخب از هر نوع منبع داشته باشد؛ اتصال چند property از یک نوع به همان سایت خارج از MVP است. OAuth و انتخاب property باید دسترسی واقعی و انطباق سایت را کنترل کنند؛ مجوز Ads account به‌تنهایی اثبات ارتباط آن با سایت نیست. هنگام تعویض property داده‌ها بر اساس integration جدا بمانند و با قبلی جمع نشوند.
- «گزارش آماده» یعنی مالکیت تأییدشده و حداقل یک منبع منتخب، یک sync موفق و معتبر برای بازه نهایی انتخاب‌شده دارد. نتیجه معتبر بدون رکورد/با صفر واقعی، گزارش خالی است؛ نبود اتصال، خطا، تأخیر، پاسخ ناقص یا permission failure گزارش موفق نیست. منابع دیگر وضعیت مستقل دارند. پس از تأیید سایت، دکمه ورود به داشبورد ابتدا همین readiness را بررسی و در صورت لزوم onboarding/دریافت داده را نشان دهد.
- **پیش‌فرض فنی:** نمای اولیه ۲۸ روز کامل منتهی به آخرین روز نهایی موجود هر منبع و مقایسه با ۲۸ روز پیش از آن؛ روز پایان برای هر منبع نمایش داده شود. روز قبل سقف انتخاب است و تأخیر نهایی‌شدن منبع می‌تواند پایان را تا سه روز عقب ببرد؛ امروز در ارزیابی قواعد وارد نشود. فیلتر سفارشیِ شامل روزهای نهایی‌نشده، وضعیت موقت/coverage واقعی نشان دهد و وارد ارزیابی قواعد نشود. sync روزانه و درخواست refresh محدودشده؛ آخرین موفقیت، بازه پوشش و کامل/موقت بودن داده نمایش داده شوند. برای ارزیابی، بازه ۲۸روزه منتهی به آخرین روز نهایی قابل دریافت هر منبع (حداکثر سه روز عقب‌تر از روز قبل) و بازه قبلی هم‌اندازه استفاده شود؛ تاریخ پایان واقعی در شواهد روشن باشد. ارزیابی فقط روی داده نهایی و sync موفق حداکثر ۷۲ ساعت گذشته انجام شود؛ داده قدیمی با برچسب نمایش داده شود، ولی توصیه جدید تولید نکند.
- timestamp عملیاتی UTC است؛ تاریخ گزارش در timezone اصلی منبع حفظ شود: timezone property در GA4، روز Pacific در Search Console و timezone حساب Ads. فیلتر UI شمسی است و به تاریخ استاندارد منبع تبدیل می‌شود؛ تبدیل روزهای منبع به روز UTC یا ادغام مقایسه بدون توضیح ممنوع است. timezone نمایشی metadata حساب/منبع را نشان دهد؛ پیش‌فرض نمایش زمان عملیاتی `Asia/Tehran` است.

GA4/Ads/GSC داده‌های attribution و پوشش متفاوت دارند. نبود داده، denominator صفر، داده thresholded/ناقص و عدد صفر واقعی چهار حالت متفاوت‌اند. گزارش Search Console تضمین همه ردیف‌ها نیست؛ top rows یا نمونه ناقص به‌عنوان کل جمعیت معرفی نشود. واحد، timezone، source، property، بازه و زمان sync همراه مقادیر حفظ شوند.

تعریف فیلدها با [GA4 Data API](https://developers.google.com/analytics/devguides/reporting/data/v1/api-schema)، [Search Analytics](https://developers.google.com/webmaster-tools/v1/searchanalytics/query) و [Google Ads Metrics](https://developers.google.com/google-ads/api/reference/rpc/v22/Metrics) تطبیق داده شده است؛ هنگام پیاده‌سازی، نسخه واقعاً انتخاب‌شده API و metadata همان property/account دوباره بررسی شود. این لینک‌ها نسخه SDK پروژه را تعیین نمی‌کنند.

### قواعد اولیه و اعتبار پیشنهاد

**انتخاب فنی با اختیار کاربر:** قواعد آغازین زیر پیشنهاد بررسی و اقدام انسانی می‌دهند؛ تشخیص قطعی علت، تضمین رشد یا تغییر خودکار کمپین نیستند. اعداد، پیش‌فرض نسخه اول موتورند و از پروپوزال اولیه منتسب نشده‌اند. تغییر آن‌ها در تنظیمات نسخه‌دار بک‌اند، با تست و وظیفه مجاز انجام می‌شود؛ UI مدیریت قواعد نداریم.

| `gsc-low-ctr-v1` | impressions ≥ ۱۰۰۰ و CTR < ۲٪ | بررسی عنوان/توضیح و query/pageهای مرتبط با شواهد؛ متوسط |
| `ga4-sessions-drop-v1` | sessions بازه قبلی ≥ ۱۰۰ و کاهش sessions ≥ ۲۰٪ در بازه فعلی | بررسی تغییرات ترافیک، tracking و کانال‌ها؛ بالا |
| `ads-cpc-rise-v1` | clicks هر دو بازه ≥ ۱۰۰ و CPC قبلی مثبت و افزایش CPC ≥ ۲۵٪، currency یکسان | بررسی keyword، auction و تغییرات کمپین؛ متوسط |

- برای قواعد مقایسه‌ای، هر دو بازه کامل و هم‌تعریف لازم‌اند. نرخ رشد روی پایه صفر محاسبه نشود؛ کلید قاعده، نسخه، ورودی‌ها، coverage و snapshot شواهد در Recommendation ثبت شوند. جزئیات شواهد، فیلد/رکورد فنی‌اند و موجودیت دامنه جدید الزامی نمی‌سازند.
- ارزیابی روزانه و cooldown هفت‌روزه برای همان rule/website/property؛ اجرای مجدد روی همان داده idempotent است. اختلاف صرفاً زمان اجرا پیشنهاد جدید ایجاد نمی‌کند. توصیه قبلی در تاریخچه باقی می‌ماند؛ قواعدی که شرطشان برقرار نیست خروجی ندارند.
- هدف سه توصیه مفید هفتگی فقط برای fixture/سایتی است که دست‌کم سه قاعده مستقل با ورودی کافی و معتبر واقعاً برقرار باشند. سایت با منابع کمتر یا بدون شرط کافی، توصیه کمتر/هیچ توصیه و توضیح کفایت داده می‌گیرد؛ اتصال اجباری یا پرکردن سهمیه با توصیه ساختگی ممنوع است.
- چون قواعد اولیه قواعد آماری ساده‌اند، محدودیت attribution، فصل‌مندی و داده منبع در توضیح آورده شود. catalog با رشد محصول در وظایف مجاز تکامل پیدا می‌کند؛ تعداد «سه» شرط تولید توصیه بی‌پشتوانه نیست.

### نسخه‌بندی و مرز اجرای این تصمیم‌ها

**انتخاب فنی:** `Frontend/`، `Backend/` و `docs/` سه مخزن مستقل‌اند. برای docs مخزن محلی مستقل بدون commit/remote اولیه ایجاد می‌شود؛ ریشه Datano مخزن یا monorepo نمی‌شود و تاریخچه دو پروژه جابه‌جا نمی‌شود. فایل‌های macOS از docs Git خارج‌اند. stage، commit، remote و push همچنان فقط با درخواست صریح انجام می‌شوند؛ تغییر مشترک باید مخزن هر فایل را در گزارش مشخص کند.

این بازبینی فقط مستندات، cookbook و راه‌اندازی Git محلی docs را تغییر می‌دهد. پیاده‌سازی هویت، دیتابیس، اتصال‌ها، رفع نقص‌های کد و ایجاد backlog مجوز ضمنی نمی‌گیرند. دو `Frontend/AGENTS.md` و `Backend/AGENTS.md` طبق درخواست کاربر بدون تغییر می‌مانند؛ شرح «وضعیت فعلی» در آن‌ها معماری آینده را لغو نمی‌کند. خواندن `docs/AGENTS.md` در همه وظایف الزامی است.

بر اساس اسناد Markdown موجود و تصمیم‌های قطعی کاربر، هدف پروژه طراحی یک **داشبورد یکپارچه تحلیل عملکرد بازاریابی دیجیتال** است که داده‌های ابزارهای گوگل را جمع‌آوری کند، شاخص‌های کلیدی عملکرد را نمایش دهد و با استفاده از یک موتور تحلیل مبتنی بر قواعد، پیشنهادهای شخصی‌سازی‌شده ارائه کند.

معماری **Modular Monolith مبتنی بر Clean Architecture** برای پیاده‌سازی تأیید شده است؛ مرزهای دامنه حفظ و از پیچیدگی عملیاتی غیرضروری پرهیز شود.

1. ثبت‌نام فعال خودکار، ورود ایمیلی، نشست امن، خروج، بازیابی رمز و پروفایل؛ مشاهده کاربران توسط مدیر.

5. ذخیره‌سازی اطلاعات تاریخی.

6. داشبورد فارسی با شاخص‌های اصلی.

7. موتور پیشنهاددهنده Rule-Based.

8. تولید گزارش و مشاهده تاریخچه پیشنهادها.

9. پنل مدیر صرفاً برای مشاهده کاربران و وضعیت اتصالات طبق UX.

10. استقرار، مستندسازی و آزمون پذیرش.

# ۳. طراحی ماژول‌های سیستم

شش حوزه زیر مرزهای مفهومی مسئولیت هستند؛ توسعه در لایه‌های موجود `Backend/app/` انجام می‌شود.

| ماژول | مسئولیت |

|---|---|

| Identity | احراز هویت، کاربران و دسترسی |

| Websites | ثبت وب‌سایت و تأیید مالکیت |

| Integrations | مدیریت اتصالات گوگل و دریافت اطلاعات |

| Analytics | استانداردسازی داده‌ها و محاسبه KPI |

| Recommendations | تعریف، ارزیابی و اجرای قواعد |

| Reporting | ارائه گزارش‌ها و داده‌های داشبورد |

تفکیک مسئولیت این حوزه‌ها با Clean Architecture انجام شود؛ الزام ساخت شش package یا لایه‌بندی تکراری برای هر حوزه نداریم.

ساختار واقعی که توسعه در آن ادامه می‌یابد:

```text
Backend/app/
├── domain/               # entities and errors
├── application/use_cases/ # domain-scoped behavior
├── interface/            # HTTP, DTOs, mappers, contracts, DI
└── infra/                # persistence, services, providers, configuration
```

Migrationهای Alembic و adapterهای SQLAlchemy/Celery در وظیفه مربوط اضافه می‌شوند؛ درخت بالا ادعای وجود آن‌ها در کد فعلی نیست. انتقال به `src/modules` و ساخت موجودیت اضافی جزو این برنامه نیست.

برای MVP از Event Bus توزیع‌شده و الگوهای پیچیده ارتباط بین سرویس‌ها استفاده نمی‌کنیم.

# ۴. طراحی جریان اصلی محصول

مهم‌ترین جریان محصول از ثبت وب‌سایت تا دریافت پیشنهاد است.

### مرحله اول: ثبت و اتصال

کاربر وارد سامانه می‌شود، وب‌سایت خود را ثبت می‌کند و مالکیت آن را تأیید می‌کند.

سپس از طریق Google OAuth اجازه دسترسی به منابع مرتبط را صادر می‌کند.

سیستم فقط منابعی را نمایش می‌دهد که کاربر مجوز دسترسی به آن‌ها را دارد.

### مرحله دوم: جمع‌آوری داده‌ها

برای هر وب‌سایت، سیستم وظایف جمع‌آوری اطلاعات را ایجاد می‌کند.

سه Adapter مستقل خواهیم داشت:

- Google Analytics Adapter

- Search Console Adapter

- Google Ads Adapter

هر Adapter اطلاعات را دریافت کرده و به مدل استاندارد داخلی تبدیل می‌کند.

داده‌های خام موردنیاز و نتایج استانداردشده در PostgreSQL نگهداری می‌شوند.

### مرحله سوم: تحلیل

سیستم داده‌های دریافت‌شده را به مجموعه‌ای از KPI تبدیل می‌کند.

| منبع | KPIهای اولیه |

|---|---|

| GA4 | sessions، totalUsers، keyEvents طبق property؛ بدون جمع کاربران یکتا در روزها |

| Search Console | Clicks, Impressions, CTR, Position |

| Google Ads | Cost, Clicks, Conversions, CPC؛ ROAS فقط با value/currency سازگار و هزینه مثبت |

تعاریف Conversion و Revenue باید متناسب با پیکربندی هر وب‌سایت مشخص شوند.

### مرحله چهارم: پیشنهاددهی

موتور قواعد، KPIها را ارزیابی کرده و پیشنهاد تولید می‌کند.

برای مثال:

**قاعده:** CTR پایین با تعداد Impression بالا.

**شرایط:**

```text

IF

impressions >= 1000

AND

ctr < 2%

THEN

Generate Recommendation

```

**پیشنهاد:**

بررسی و بهینه‌سازی عنوان و توضیحات متای صفحات مرتبط.

این مثال به قاعده آغازین `gsc-low-ctr-v1` مربوط است؛ دوره، کفایت داده، نسخه و cooldown طبق تصمیم‌های بالای همین سند اعمال شوند.

هر پیشنهاد باید شامل توضیح، داده‌های پشتیبان، اولویت عملیاتی و وضعیت پیگیری باشد.

# ۷. ملاحظات حیاتی پیاده‌سازی

سه موضوع باید از ابتدای پروژه کنترل شوند.

**اول: دسترسی به سرویس‌های گوگل.** استفاده از Proxy نباید پیش‌فرض معماری باشد. ابتدا باید دسترسی قانونی و عملی به APIهای موردنیاز، شرایط حساب‌های آزمایشی و محدودیت‌های هر سرویس بررسی شود. مسیرهای ارتباطی نیز باید از نظر امنیت و انطباق با شرایط استفاده سرویس‌ها ارزیابی شوند.

**دوم: امنیت داده‌ها.** توکن‌های گوگل باید به‌صورت رمزنگاری‌شده نگهداری شوند. جداسازی داده‌های وب‌سایت‌ها باید در Backend اعمال شود و صرفاً به محدودسازی رابط کاربری متکی نباشد.

**سوم: کیفیت پیشنهادها.** تولید سه پیشنهاد در هفته به‌تنهایی نشانه کیفیت موتور نیست. باید برای هر قاعده، شرایط اجرا، شواهد، موارد استثنا و امکان جلوگیری از تکرار پیشنهاد تعریف شود.

این ملاحظات الزامات صحت داده، جداسازی مالک و امنیت همین اسناد Markdown را تکمیل می‌کنند؛ منبع اولیه دیگری لازم نیست.

کلاینت type-safe فرانت‌اند با Orval از OpenAPI واقعی بک‌اند تولید شود؛ فایل generated دستی ویرایش نشود.

# ۸. تعریف نهایی MVP و معیار پذیرش

MVP زمانی آماده تحویل است که کاربر بتواند از ابتدا تا انتها سناریوی زیر را اجرا کند:

**ثبت‌نام ← ثبت وب‌سایت ← تأیید مالکیت ← اتصال منابع گوگل ← جمع‌آوری اطلاعات ← مشاهده داشبورد ← دریافت پیشنهادهای شخصی‌سازی‌شده**

شرایط پذیرش هدف MVP (به معنی تکمیل فعلی نیست):

| معیار | وضعیت مورد انتظار |

|---|---|

| منابع داده | سه سرویس گوگل |

| مالکیت وب‌سایت | تأییدشده |

| ذخیره اطلاعات | تاریخی و قابل بازیابی |

| داشبورد | فارسی، یکپارچه و عملیاتی |

| پیشنهاددهنده | مبتنی بر قواعد قابل‌توضیح |

| تعداد پیشنهاد | هدف سه توصیه مستقل در fixture واجد شروط سه قاعده؛ بدون توصیه ساختگی برای داده/شرط ناکافی |

| امنیت | کنترل دسترسی و حفاظت از Credentialها |

| آزمون | Unit، Integration و E2E |

| استقرار | Docker Compose |

| مستندات | OpenAPI، راهنمای نصب و راهنمای کاربر |

**نتیجه:** خروجی این نقشه، یک محصول بتای عملیاتی است، نه صرفاً یک Dashboard نمایشی. معماری تأییدشده امکان توسعه موتور تحلیل، افزودن منابع داده جدید و تکامل محصول را فراهم می‌کند، بدون آنکه MVP را درگیر زیرساخت‌های غیرضروری کند.
